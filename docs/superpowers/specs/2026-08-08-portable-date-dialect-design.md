# Portable date dialect, configured at `make setup`

## Problem

Grampa is BSD/macOS-only today, and the whole of that lock-in is one command: `date`. The
Makefile builds `date -v<y>y -v<m>m -v<d>d` selectors — the BSD dialect — in a single helper
(`date_args`) shared by three call sites: the long-form page date (`date_from_filename`), the
RFC-822 feed date (`rfc822_from_filename`), and the parse-time date check (`BAD_POST_DATES`).
On GNU coreutils those selectors are rejected, so a legal build fails.

A probe of the target machine (`tools/probe-platform.sh`, run on Arch Linux, GNU Make 4.4.1 /
coreutils 9.11) confirms that **everything else grampa depends on already behaves identically
on GNU**: the specific-over-generic pattern-rule choice, `sort -t- -k1,1n`, `sed` address-and-
quit, `awk` `ENVIRON` + `getline`, `cat -vt`, and raw-byte `ls` all match the documented BSD
behaviour. The port is `date` and nothing else.

## Goal

Make grampa build unmodified on both BSD/macOS and Linux/GNU, choosing the `date` dialect once
per install at `make setup` time — the conventional `./configure`-writes-`config.mk` idiom —
rather than at every build. A build on an unconfigured tree fails loudly with instructions to
run `make setup` first.

Settled with the user, not open for the reviewer to relitigate:

- **Portable, not GNU-only.** Both dialects stay supported; the mac keeps building.
- **Detected at `make setup`, persisted, not probed per build.** The user never moves a
  checkout across OSes, so a cached dialect cannot go stale in their workflow. This is the
  deliberate trade against the stateless parse-time-probe alternative.
- **An unconfigured build fails loud** ("run `make setup` first"), rather than falling back to
  a live probe.

## Design

### 1. The configure mechanism: `config.mk` + `-include`

`make setup` gains a probe step. It tests the dialects in order and writes the winner to a
generated `config.mk` at the repo root:

```sh
if date -v1d >/dev/null 2>&1; then dialect=bsd; \
elif date -d 2026-01-15 >/dev/null 2>&1; then dialect=gnu; \
else echo "grampa: no supported date dialect (need BSD 'date -v' or GNU 'date -d')" >&2; \
     exit 1; fi; \
echo "DATE_DIALECT := $$dialect" > config.mk
```

BSD is tested first and short-circuits, so GNU's `-d` is never handed to a BSD `date`. The
order mirrors `tools/probe-platform.sh`. If neither dialect works, setup errors and writes no
`config.mk` — leaving the tree unconfigured rather than half-configured.

The Makefile pulls the result in at the top:

```make
-include config.mk
```

The leading `-` means "include if present, silently skip if absent." `include` is processed at
**parse time**, so `$(DATE_DIALECT)` is in scope both for the parse-time `BAD_POST_DATES` check
and for the recipes.

`config.mk` is per-install and gitignored, sitting beside `config` and `deploy.sh` — the other
two per-install files — at the repo root, **not** in `work/`, so `make clean` does not wipe it.

Unlike `config` and `deploy.sh`, `config.mk` has **no `.source/config.mk.example`**: it is
*generated by probing the machine*, not copied from a template. This also means setup **always
(re)writes** `config.mk` on every run — the one deliberate exception to setup's otherwise
non-clobbering `yes n | cp -i` rule, justified because the file is derived, not authored. A
re-run of `make setup` is therefore what re-fixes the dialect if a checkout ever does move
between OSes.

### 2. The factored dialect branch: one place, two twins

`date_words` — the `2026 07 04` three-field split of a filename — stays shared and
dialect-independent. The current `date_args` is replaced by a `date_select` chosen by
`$(DATE_DIALECT)`, in grampa's existing "visible twin" style:

```make
# date_words: the date's three fields as words (2026 07 04) -- shared, dialect-free.
date_words = $(wordlist 1, 3, $(subst -, , $(notdir $(1))))

# date_select: the arguments that name that day at midnight, one twin per dialect.
#   bsd: -v2026y -v07m -v04d -v0H -v0M -v0S
#   gnu: -d "2026-07-04 00:00:00"
ifeq ($(DATE_DIALECT),bsd)
date_select = $(join $(addprefix -v,$(call date_words,$(1))),y m d) -v0H -v0M -v0S
else ifeq ($(DATE_DIALECT),gnu)
date_select = -d "$(subst $(space),-,$(call date_words,$(1))) 00:00:00"
else
date_select = $(error grampa: no DATE_DIALECT -- run `make setup` first)
endif
```

All three call sites consume `date_select`, so the check still runs the *exact* arguments the
build runs — the correctness property the existing `date_args` comment guards:

```make
date_from_filename   = $(shell date $(call date_select,$(1)) "+%B %d, %Y")
rfc822_from_filename = $(shell LC_ALL=C date $(call date_select,$(1)) "+%a, %d %b %Y %H:%M:%S %z")
BAD_POST_DATES := $(if $(SUSPECT_POST_DATES),$(shell $(foreach n,$(SUSPECT_POST_DATES),\
                     LC_ALL=C date $(call date_select,$(n)) >/dev/null 2>&1 || echo $(n);) true))
```

Two things move relative to today's code:

- **The midnight pin folds into `date_select`.** Today only `rfc822_from_filename` and the
  check carry `-v0H -v0M -v0S`; `date_from_filename` omits them because its `%B %d, %Y` format
  prints no time. Under the new `bsd` twin the pin is always present. This is output-preserving:
  `%B %d, %Y` prints no time component, so pinning it changes nothing the page shows. Keeping
  the pin in one place is what lets a single `date_select` serve all three sites in both
  dialects. GNU carries the pin as the literal `00:00:00` in the `-d` string, always, for the
  same reason `rfc822` needs it: `date -d "y-m-d"` alone keeps the current wall-clock time.
- **`LC_ALL=C` stays on `rfc822_from_filename` and the check** in both dialects — RFC 822 day
  and month names are literal English tokens under either `date`.

The GNU `-d` argument quotes the date string, so the embedded space survives the shell:
`date -d "2026-07-04 00:00:00" "+..."`. The filename fields are digits (already constrained by
`BAD_CHARS` and cleared by the date check), so nothing author-controlled reaches that string.

### 3. Failing loud when unconfigured

The `else` branch of `date_select` is `$(error ...)`. The failure must fire on a real build but
**never during `make setup` itself**, or `setup` could not create the `config.mk` that resolves
it. Two things together guarantee that:

1. `setup`'s own recipe copies files and writes `config.mk` without ever expanding a date
   helper, so it never reaches `date_select`.
2. **The parse-time check `BAD_POST_DATES` is gated on `$(DATE_DIALECT)`** — it only runs when a
   dialect is configured:

   ```make
   BAD_POST_DATES := $(if $(DATE_DIALECT),$(if $(SUSPECT_POST_DATES),$(shell ...date_select...)))
   ```

   Without this gate the check is a latent deadlock: `BAD_POST_DATES` is `:=`, so it expands at
   parse time on *every* invocation, `make setup` included. On an existing install with a
   month-end post (`SUSPECT_POST_DATES` non-empty) and no `config.mk` yet, that parse-time
   `$(shell)` would expand `date_select`, whose `else` branch `$(error)`s — killing `make setup`
   *before its recipe runs*, so `config.mk` is never written and the next `make setup` dies
   identically. You could neither build nor configure. The gate closes it: unconfigured, the
   check is simply skipped.

The result is a **uniform** failure story rather than the parse-vs-recipe split an earlier draft
described:

- `make setup` **always succeeds** and writes `config.mk`, for any corpus — virgin, 1st–28th,
  or month-end. No deadlock.
- Any real build on a tree with no `config.mk` dies at **recipe time**, when the first dated
  page's `date_from_filename` expands `date_select`, with
  `grampa: no DATE_DIALECT -- run 'make setup' first`. (The check no longer contributes a
  parse-time variant, because it is gated off when unconfigured.) A tree with no posts needs no
  date and raises nothing — and fails earlier on the missing `templates/` anyway.

Gating the check costs no date validation: when a dialect *is* configured the check runs exactly
as before, and an unconfigured build still fails loud one step later at the recipe. This is the
clean upgrade path for an existing BSD install: pull the new Makefile → `make setup` (which now
always succeeds, non-clobbering for everything but the generated `config.mk`) writes
`DATE_DIALECT := bsd` → builds resume, byte-identical to before.

### 4. Ripple

- **`.gitignore`:** add `/config.mk`, anchored, in the per-install group with `/config` and
  `/deploy.sh`.
- **`make clean`:** unchanged — it wipes `build/` and `work/` and leaves `config.mk`, exactly as
  it leaves `config`. Configure once; build and clean many.
- **Tests (`tests/run.sh`):** existing build tests need no change — `sandbox()` already runs
  `make setup` (line 31), so every sandbox gets a `config.mk` for its host automatically. Add
  two tests:
  - `test_setup_writes_the_host_date_dialect` — after `make setup`, `config.mk` exists and its
    `DATE_DIALECT` is one of `bsd`/`gnu` and matches a direct probe of the host's `date`.
  - `test_build_without_config_mk_fails` — remove `config.mk` after setup, add an **ordinary
    1st–28th-dated post** (so `SUSPECT_POST_DATES` is empty and the failure comes at recipe
    time, the representative case), build, and assert non-zero exit and the "run `make setup`
    first" message. A month-end post would fail earlier at parse time on the same message; the
    test pins the recipe-time path deliberately rather than leaving which path fires incidental.
  - `test_migration_reports_error_when_rm_fails` (an **existing** BSD-only test) must be guarded
    to skip cleanly where its `chflags uchg` immutability trick is unavailable — see the ripple
    item below. Without the guard `make test` cannot be green on the GNU target, which defeats
    the port's own premise.
- **`CLAUDE.md`:** rewrite the **BSD-only** gotcha into a "portable, dialect chosen at `make
  setup`" note; add `config.mk` to the Layout table as a per-install generated file (no
  `.source` twin); document the recipe-time unconfigured-build failure and the `BAD_POST_DATES`
  gate; insert `date_words`/`date_select` into the helper list (there is no `date_args` reference
  in CLAUDE.md to rename — it names `date_from_filename`/`rfc822_from_filename` only); fix the
  now-stale standalone Gotchas bullet that says `rfc822_from_filename` pins midnight with
  `-v0H -v0M -v0S` (the pin lives in `date_select` now). **Also correct the "Serial `make setup
  all` is fine" claim in the setup section:** after this change it is fine only when `config.mk`
  already exists or `posts/` is empty. On a tree that already has dated posts, `make setup all`
  in one process still fails — `-include config.mk` runs once at parse time (empty on a virgin
  tree), setup's recipe then writes `config.mk`, but make does not re-include a fileless-rule
  include mid-run, so the `build` half of the *same* process still has `DATE_DIALECT` empty and
  fires the `$(error)` at recipe time (uniformly now, since the parse-time check is gated off
  when unconfigured). The difference from before the B1 gate: `make setup`'s recipe *does* run
  and write `config.mk`, so **a second `make` succeeds** — no deadlock. This is loud,
  self-correcting, and consistent with the existing "setup wants its own invocation" guidance —
  the same lazy-parse-vs-recipe split already documented for `config`/`FEED_PAGES`, reaching an
  `-include` this time — but it must be written down rather than left contradicting the current
  "is fine" sentence.
- **`tests/run.sh` — guard the BSD-only migration test:** `test_migration_reports_error_when_rm_fails`
  makes a file un-removable with `chflags uchg` (BSD/macOS only). On GNU that is a no-op or
  `command not found`, so `rm` succeeds and the test's 4 assertions fail — 4 red on the very
  platform this branch ports *to*. Guard the test to detect immutability support (e.g. `command
  -v chflags`) and skip with a printed note where it is unavailable, so `make test` is green on
  both platforms. Pre-existing and unrelated to `date`, but a port whose acceptance criterion is
  "`make test` passes on Linux" cannot leave it red; it is in scope as the code a good developer
  fixes in the file they are already porting.

### 5. One behavioral difference: documented, not fixed

A two-digit-year filename such as `26-7-4-home_x.txt` renders its **displayed** date as year
`0026` under BSD (`date -v26y`) but `2026` under GNU (`date -d "26-7-4 ..."`). The URL is
unaffected — paths come from the raw filename fields via `path_from_filename`, not from `date`,
so the post lives at `/26/7/4/x.html` under either dialect. This is an edge case (posts are
conventionally dated with four-digit years and zero-padded for the URL's sake anyway); it is
documented in CLAUDE.md's dialect note, not blocked.

## What this does not do (YAGNI)

- No `.source/config.mk.example`, no `configure` script, no autotools — `make setup` is the
  configure step and a one-line probe is the whole of it.
- No per-build dialect probe and no dialect override env var — the user's workflow never needs
  either, and both add a second code path to keep tested.
- No attempt to normalise the two-digit-year rendering difference between dialects.

## Test plan

Run `make test` on this GNU host. It must reach **green once the `chflags` migration test is
guarded** (§4) — the date port itself fixes the 7 previously-BSD-only failures unrelated to
`chflags`; without the guard the suite stays red at 4 (`test_migration_reports_error_when_rm_fails`),
which is why that guard is in scope rather than deferred. The suite then exercises the `gnu`
twin end-to-end. The two new tests above cover detection and the unconfigured-build failure. The
existing date-rendering, RSS-`pubDate`, and parse-time date-check tests re-verify that legal
dates render and illegal ones are rejected under the detected dialect.

A live run of the **`bsd` twin** cannot happen on this GNU host — its `date` string is today's
production BSD args plus the already-in-production `-v0H -v0M -v0S` fold, so it is output-preserving
by the reasoning verified for the `gnu` twin, but it wants a BSD/macOS smoke test at the
branch-review checkpoint before merge. `tools/probe-platform.sh` remains the artifact for
confirming a *new* target platform before trusting it.
